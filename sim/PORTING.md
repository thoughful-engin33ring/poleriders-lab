# Native Pole Riders simulator: porting rules

Goal: a native (arm64, -O2) reimplementation of one Super Pole Riders match (Flatirons first, other
levels later) that is **bit-exact** with the real game where possible: same Box2D world, same
bodies/fixtures/joints created in the same order, same per-tick game logic, same float arithmetic.
The real game is the oracle (see "Oracle" below); every ported function will be checked
tick-by-tick against it.

## Layout
- `sim/Box2D/` — Box2D 2.1.2 as compiled into the game (patched to match; see BOX2D_DIFF.md).
  Pristine source: `sim/third_party/Box2D_v2.1.2/`.
- `sim/src/x86math.h` — `x86_sinf/x86_cosf`: arm64 libm sinf/cosf differ from the game's
  (x86_64 macOS libm) on ~27k specific float inputs; these reproduce the x86 results bit-exactly
  (table generated by `sim/tools/libm/`). atan2f, sqrtf, fmodf, floorf, fminf, fmaxf are identical
  natively. Other libm functions (acosf, asinf, expf, logf, powf, tanf, double sin/cos/pow/exp) are
  NOT identical — if gameplay code calls any of them, say so in your report.
- `sim/src/game/` — the ported game code. `sim/re_notes/` — RE notes (layouts, function maps).

## Rules for ported code
1. **Same names.** Keep the original class/method structure and names (`PoleRiders::PlayState::Update`,
   `Player::_UpdateSticks`, …). Every ported function starts with a comment giving the original
   symbol and address, e.g. `// PoleRiders::PlayState::Update() @ 0x10013b8c8`.
2. **Same memory layout** for game objects: fields live at the same byte offsets as in the binary
   (both are LP64, so pointers/ints/floats line up). Use plain structs with named fields, explicit
   `uint8_t _pad_XXX[n]` for unknown/unused regions, and `static_assert(offsetof(T, f) == 0x...)`
   for every named field and `static_assert(sizeof(T) == ...)`. This lets the oracle diff raw object
   bytes (with pointer fields masked). Vtable slots at offset 0 are `void *_vtbl` placeholders; do not
   rely on C++ virtual dispatch for game classes unless the layout still matches.
3. **Exact float semantics.** Reproduce the precision and order of every operation as compiled:
   `mulss/addss` = float, `cvtss2sd ... mulsd` = double math (write it as double in C++), literal
   constants with their exact values (use hex-float literals when not exactly representable in
   short decimal; `re/dz.py ADDR N` resolves RIP-relative literals). Never let the compiler reassociate
   (we build with `-ffp-contract=off`, no fast-math). Use `x86_sinf/x86_cosf` for sinf/cosf.
   Inlined Box2D helpers (b2Vec2 ops, b2Mul, etc.) are fine to call as normal Box2D functions — they
   compute the same thing.
4. **Same Box2D call sequence.** Body/fixture/joint creation and destruction order, SetTransform,
   SetLinearVelocity, ApplyForce/Impulse/Torque, SetAwake, filter changes, etc. must happen in the
   same order with the same arguments: Box2D's results depend on list order and proxy ids.
5. **Skip presentation**: drawing, particles (Dust/Sparks/Flare/ShockWave visuals), sound, camera,
   music, UI text, rumble, achievements. BUT keep anything that feeds back into gameplay state (a
   timer that gates logic, a random() call that advances the RNG, hit-stop/punch time, etc.). If a
   skipped function writes a field that gameplay later reads, port that part.
6. **random()**: the game calls libc `random()`. If a gameplay-relevant value depends on it, note
   where; the sim will carry a per-match BSD `random()` state (so matches can run in parallel).
7. **Input**: the sim receives the same per-pad stick values the bridge feeds the real game
   (`farm act`: lx, rx, ry per pad, SDL convention +y down) and must reproduce the engine's input
   chain (atrophy::Gamepad::setJoystickPosition -> Common::Input::_UpdatePad -> what Player reads).
8. Code style: C++17, one .cpp per original class where sensible, no exceptions, no RTTI needs.
   Build: `make -C sim` (arm64, `-O2 -ffp-contract=off -fno-fast-math`).

## Oracle
The bridge (`bridge/sprbridge.c`, `bridge/farm.c`) runs the real game's PlayState headlessly
("shadows") and will expose raw dumps of every Box2D body/fixture/joint and game object per tick.
The sim will produce the same dump format; `sim/tools/diff_trace.py` reports the first differing
field and tick.
